# User manual

## Services

```sh
sudo systemctl status klipper moonraker nginx
sudo systemctl restart klipper
journalctl -u moonraker -f
```

Logs that matter are `~/printer_data/logs/klippy.log` and
`~/printer_data/logs/moonraker.log`.

## G-code commands

Entered in Mainsail's console.

| Command | Effect |
|---------|--------|
| `FIRMWARE_RESTART` | Reload config and reset the MCU. Use after a config error. |
| `RESTART` | Restart the Klipper host only. |
| `G28` | Home all axes. Z homes at the probe point. |
| `PROBE_CALIBRATE` | Start the probe Z offset procedure. |
| `TESTZ Z=-0.1` | Step down during calibration. `Z=+0.02` steps up. |
| `ACCEPT` | Finish a calibration at the current position. |
| `ABORT` | Leave a calibration without saving. |
| `SAVE_CONFIG` | Write pending values into `printer.cfg` and restart. |
| `BED_MESH_CALIBRATE` | Probe the bed and build a mesh. |
| `BED_SCREWS_ADJUST` | Walk the nozzle to each bed screw in turn. |
| `PID_CALIBRATE HEATER=extruder TARGET=200` | Tune hotend PID. |
| `SET_GCODE_OFFSET Z_ADJUST=0.02 MOVE=1` | Nudge Z during a print. |
| `M112` | Emergency stop. |

`SAVE_CONFIG` rewrites `printer.cfg`, appending an autogenerated block at the
end. Do not edit below the marker it adds.

## Editing the config

`~/printer_data/config/printer.cfg` is editable from Mainsail's Machine tab or
over SSH. Klipper validates on restart and refuses to start on a bad config,
reporting the offending line in `klippy.log` and in Mainsail.

## Input shaping

### Wiring

ADXL345 to the Pi Zero 2 W, SPI0:

| Module pin | Board pin | Signal |
|---|---|---|
| VCC | 1 | 3V3 |
| GND | 6 | GND |
| SDA | 19 | MOSI |
| SDO | 21 | MISO |
| SCL | 23 | SCLK |
| CS | 24 | CE0 |
| INT1 | — | n/c |
| INT2 | — | n/c |

### Measuring

Requires `[include adxl345.cfg]` uncommented in `printer.cfg`.

```
FIRMWARE_RESTART
ACCELEROMETER_QUERY
```

`ACCELEROMETER_QUERY` returns a live acceleration vector. Roughly 9.8 m/s² on
one axis and near zero on the others means the chip is talking.

This is a bed slinger, so the sensor has to move to the mass under test. Mount
it on the print head, then:

```
TEST_RESONANCES AXIS=X
```

Move it to the bed plate, then:

```
TEST_RESONANCES AXIS=Y
```

Each run writes a CSV to `/tmp/`. Process them into a recommendation:

```sh
~/klipper/scripts/calibrate_shaper.py /tmp/resonances_x_*.csv -o /tmp/shaper_x.png
```

Copy the CSVs to a workstation if the plots are slow to generate; the Pi has
425 MB of RAM and matplotlib is the heaviest thing that runs on it.

The script prints a recommended shaper type and frequency per axis, which go
into an `[input_shaper]` section:

```ini
[input_shaper]
shaper_freq_x: <from the X run>
shaper_type_x: <from the X run>
shaper_freq_y: <from the Y run>
shaper_type_y: <from the Y run>
```

Y usually comes out lower than X on a bed slinger, because the bed carries more
mass than the head.

## Rebuilding and flashing firmware

Needed when a Klipper update changes the MCU protocol, or when a config option
that lives in the firmware changes.

```sh
cd ~/klipper
make menuconfig     # settings below
make clean
make
```

Settings for this printer:

| Option | Value |
|--------|-------|
| Micro-controller architecture | STMicroelectronics STM32 |
| Processor model | STM32F103 |
| Bootloader offset | 28KiB bootloader |
| Communication interface | Serial (on USART1 PA10/PA9) |
| Baud rate | 250000 |

The build writes `out/klipper.bin`.

To flash, copy that file to a FAT32 SD card of 32 GB or smaller, formatted with
4096-byte clusters, under a filename the bootloader has not seen before. Use the
`fwMMDDx.bin` pattern, 8.3-safe, because whether this bootloader reads long
filenames varies between board batches.

```sh
sudo mkfs.vfat -F 32 -s 8 -n ENDER3V2 /dev/sdX1
```

Only one `.bin` may be on the card. The bootloader flashes what it finds, so a
second binary makes the outcome ambiguous.

Then: power the printer off, insert the card, power on and wait about 15
seconds, power off, remove the card, power on.

Record the new filename, Klipper commit and md5 in the table in
[../README.md](../README.md).

### How to tell the flash worked

The LCD is not the indicator. It shows a frozen "Creality" splash whenever
Klipper is running, and it does that whether or not the flash you just attempted
succeeded.

Check from the Pi:

```sh
sudo systemctl restart klipper
curl -s http://127.0.0.1/printer/info
```

`"state":"ready"` means the MCU answered. Watch `klippy.log` for a `freq=`
close to 72000000, which confirms the clock is right.

If the bootloader declined the file, the printer comes back on the old firmware
and Klipper reports `Unable to connect`. The fix is a new filename, not a
rebuild.

## When Klipper will not connect

Work through these in order.

1. Is the printer powered on? The CH340 draws its power from the printer, so
   with the printer off there is no USB device at all. `lsusb` on the Pi shows
   only the root hub.
2. Does `/dev/serial/by-id/usb-1a86_USB_Serial-if00-port0` exist? If not, check
   `sudo dmesg | tail` for enumeration. Note that the device takes a few seconds
   to appear after the printer powers on.
3. Does `~/printer_data/logs/klippy.log` report a config error rather than a
   connection error? Config errors name the line.
4. Is the MCU still running Marlin? A failed flash looks exactly like a
   connection failure.

## Rolling back to Marlin

Download the Creality stock firmware for the 4.2.7 board, BLTouch variant, from
Creality's download centre. Put it alone on the SD card, under a filename not
used before, and flash the same way.

The LCD returns with Marlin.
